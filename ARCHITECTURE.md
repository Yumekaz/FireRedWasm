# FireRed native browser port: architecture and baseline audit

Audit date: 14 November 2026. Target: English Pokémon FireRed 1.0 from pret, built from source for wasm32. This document proposes future work; no port code, browser build, or gameplay milestone was completed in this audit.

## Decision

Compile FireRed's C into WebAssembly, and translate its assembly **data** into relocatable Wasm objects. Replace ARM startup and the hardware-facing routines with scoped host shims. Keep the existing GBA build and its checksum target. The browser provides input, a clock, pixels, audio output, and save storage; FireRed owns game state, callbacks, script dispatch, maps, battles, and rules.

The game's existing event and battle bytecode engines are compiled game logic. Keeping them does not mean interpreting a GBA ROM: the browser will never execute ARM instructions, boot a BIOS, load a ROM for execution, or fall back to an emulator. ARM routines that still matter must be replaced at their API boundary or ported to C with parity tests.

## FireRed baseline: upstream passed, local run blocked
v
[FireRed's Makefile](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/Makefile) builds host tools first, generates maps and other data, and runs the host preprocessor and `preproc` with `charmap.txt` before agbcc or modern GCC compiles game C. GNU ARM binutils assemble the resulting code and script/data assembly and link the GBA ELF with the selected linker script. gbafix updates the header in the ELF, and objcopy emits the ROM. `make compare` checks `pokefirered.gba` against [firered.sha1](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/firered.sha1): `41cb23d8dccc8ebd7c649cd8fbb58eeace6e2fdc`. The normal build consumes data in the checkout; it does not require an input base ROM.

Provision a supported build environment before changing game code. The [pinned INSTALL.md](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/INSTALL.md) covers WSL and devkitPro/MSYS2. Prefer Linux (or WSL with source in its Linux filesystem) for repeatable baselines. The matching build needs Bash/coreutils and a SHA-1 checker, GNU make, host C/C++ (including C++17 for some tools), pkg-config and libpng/zlib development headers, ARM binutils, and [pret/agbcc](https://github.com/pret/agbcc) built and installed into the checkout. The modern ARM build additionally needs ARM GCC and its target libraries, including libc/libgcc/libnosys; follow the upstream CI package setup or use devkitARM. Header/library availability was not tested because the local build never reached the host tools.

Example reproduction in a provisioned Debian/Ubuntu environment, from the parent of a fresh pinned `pokefirered` checkout:

```sh
sudo apt install build-essential binutils-arm-none-eabi git pkg-config libpng-dev zlib1g-dev
git clone https://github.com/pret/agbcc.git
(cd agbcc && ./build.sh && ./install.sh ../pokefirered)
(cd pokefirered && make -j"$(nproc)" compare)
```

Use the pinned repo's modern setup to run `make -j"$(nproc)" modern` separately; it is a second build check, not the checksum oracle. Record the actual FireRed and agbcc SHAs, tool versions, command output and digest when this runs. Keep both builds in local or ephemeral CI storage; do not upload ROM artifacts. No system packages were installed during the audit.

## How Emerald crosses the hardware boundary

- **Compilation.** [Its Makefile](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/Makefile#L273) orchestrates host generators, builds game C with `clang --target=wasm32-unknown-unknown -DMODERN=1 -DWASM=1` through `preproc`, and assembles translated data with Clang. It links without ARM startup using wasm-ld, `--no-entry`, `--allow-undefined`, `--export-all`, and fixed 256 MiB initial/max linear memory. The linked module exports `AgbMain` and `WasmRunFrame`. The native build is a separate target, not how the browser works.
- **Memory, interrupts and display.** [main.c](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/src/main.c#L96) returns from startup in Wasm and lets the host call one frame at a time. It invokes VBlank from that frame path rather than waiting on the GBA's IRQ hardware. GBA addresses for registers, palettes, VRAM and OAM remain valid offsets within the large Wasm memory. [DMA macros](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/include/gba/macro.h#L282) replace immediate copies with software copies; [wasm_display.c](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/src/wasm_display.c) consumes the register state and HBlank DMA settings and draws tile backgrounds, sprites, windows, blending and selected bitmap modes into a 240×160 RGBA buffer. That models the parts the game uses; it is not evidence of cycle-accurate interrupts, timers, DMA, or PPU behavior.
- **Pointers and scripts.** [wasm_asm_data.py](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/tools/wasm_asm_data.py) expands/preprocesses source, loads Emerald-specific constants and tables, and emits labels and fixed-width data for maps, map events, field scripts, battle scripts, AI scripts and animation scripts. Data `.4byte symbol` references resolve to linked linear-memory addresses. Function references use a different relocation/table mechanism: declarations such as `.functype` and generated `WasmSpecial_*` wrappers let the linker or compiler create entries with the signature expected by indirect calls, including wrappers for void specials. The desktop port's pointer token bridge in `tools/native/native_engine.c` addresses wider host pointers; it is not part of browser wasm32. A 32-bit word in a script can also be a number or a virtual address, so it cannot be treated as a pointer generically.
- **Assets and sound.** [generate_wasm_assets.py](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/tools/generate_wasm_assets.py) discovers `INCBIN`/`INCGFX` inputs, makes missing generated files and uses gbagfx for conversions. The preprocessor turns game text and binary asset references into compiler input. [generate_wasm_sound.py](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/tools/generate_wasm_sound.py) reads the Emerald song table and MIDI options, uses mid2agb, and emits player/song duration metadata: the [Wasm m4a branch](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/src/m4a.c#L28) advances player state with frame countdowns. This is a timing approximation and is not a faithful MIDI/sample mixer or evidence that Web Audio plays the original soundtrack.
- **Browser host.** [web/app.js](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/web/app.js) fetches and instantiates Wasm, wires BIOS operations such as CpuSet/LZ77/RL/affine calculations, writes active-low buttons, advances game frames from a `requestAnimationFrame` accumulator, and uses Canvas 2D to display the buffer. Flash is represented by 128 KiB at `0x0E000000`, with localStorage, save import/export and Emerald-specific migration. Unrecognized function imports return zero; that permissive behavior can conceal missing work. Its [frame replay tool](https://github.com/tripplyons/pokeemerald-wasm/blob/fd83f5b6e609b61b0b10777e32c74343e1a81b41/tools/wasm_replay.mjs) drives the actual frontend at recorded frame numbers and captures screenshots and errors.

## FireRed implementation boundary

| Area | Reuse the approach | FireRed work and failure checks |
| --- | --- | --- |
| Build and source ownership | Separate Wasm target, host tools, generated objects, small C ABI. | Pin pret in a local source checkout and apply a narrow, reviewable port patch series; keep port rules outside the original default graph (for example `port/wasm.mk`). Use Clang/LLD with wasm32, host GCC/G++ and libpng/zlib, Python 3, and Node for local serving/replay. Emscripten and uv are unnecessary if our rules invoke Clang/Python directly. Pin versions before CI. Use explicit exports and no blanket undefined imports. Build and compare GBA before and after every patch batch, including without the Wasm toolchain present. |
| Frame and registers | Returning initializer and repeatable frame step, BIOS behavior in software, renderer reads committed hardware state. | [FireRed main.c](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/src/main.c#L100) has ARM inline RAM clearing even with `MODERN=1`, an ARM IRQ entry and a spin wait. Preserve its callback order, key repeat/help behavior, DMA manager, VBlank side effects (including RNG advancement), timer-based Trainer ID seed, and soft reset. Inventory `src/crt0.s`, `libagbsyscall.s`, remaining inline ARM, flash RAM code, RFU and multiboot. Prefer compact register/VRAM/OAM/palette arrays exposed by port macros and explicitly translate audited fixed addresses; Emerald's high-address layout is a fallback only if measured and collision-proof. Never treat arbitrary constants or null reads as real host memory. |
| Scripts and ABI | Expand actual data macros and let the linker relocate symbols. Use typed wrappers and byte-based little-endian reads for packed data. | [FireRed's command table](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/data/script_cmd_table.inc) is raw ordered `.4byte ScrCmd_*`, unlike Emerald's named entries. Generate from FireRed table order and actual macro definitions; preserve signatures, table bounds, duplicate special slots, conditionals and layout. Audit field scripts, map headers/events, special variables, movement and field effect tables, battle/AI/animation scripts, and FireRed trainer battle argument forms. Audit `callnative` vs `gotonative`, RAM/virtual Mystery Gift script addresses, any absolute pointers and pointer-width bitfields. Separate numeric values, memory relocations and function table entries. Fail on unknown directives, unresolved symbols or signature mismatches. Test offsets/sizes and link- or runtime-validate indirect calls; do not paper over errors with casts or zero returns. |
| Assets and graphics | Rebuild generated assets from local pinned inputs; small renderer ABI returning RGBA. | Prefer FireRed's mapjson/jsonproc, graphics and audio rules, and FireRed's signed and unsigned `INCBIN`/charmap preprocessor. Account for assembly includes and `.incbin` as well as C inputs. Compare tile/palette/font/text bytes and map records against independently generated GBA data, normalizing relocations. Validate FireRed title effects, fonts, sprite priority, windows, affine math and scanline DMA with fixtures/replays before optimizing. |
| Sound and persistence | Keep sound and flash at hardware boundaries and persist completed save data in the host. | Port FireRed's m4a ARM mixer/sequencer behavior (including cry, fanfare/status and fades), song tables and sample data; browser audio is only an output sink. A muted initial build still needs the completion state for waits it reaches. Preserve `save.c` sector packing, counters, checksums, save-slot recovery and FireRed/Quest Log state. Verify a 128 KiB sector-backed .sav using FireRed fixtures; do not use Emerald save offsets or migrations. Put completed snapshots in IndexedDB with explicit import/export and report persistence failures. |
| Features outside the first slice | Use narrow, visible capability boundaries. | Defer cable/RFU, Mystery Gift downloads, e-Reader/GC multiboot and Switch rev10 SVC hooks; profile English rev0 explicitly. Flag unsupported external paths at their platform boundary. No new network or GPU requirements for the initial browser build. |

For interactive milestones, use an API such as `FireRed_Init`, `FireRed_Step(buttons)` and `FireRed_Framebuffer` (names proposed). JS should read a declared buffer range, draw in Canvas 2D and pace a bounded fixed-step simulation at GBA cadence (about 59.73 Hz), independent of screen refresh. Exact-frame test mode must be independent of wall-clock time and allow a recorded seed/timer input. Pause cleanly when hidden, clear held input on blur and avoid unbounded catch-up. Put short C BIOS/DMA shims in the core where practical so headless tests use the same code. Treat impossible pointer targets, unimplemented reached services and memory traps as explicit test failures.

## Smallest genuine proof of concept (proposed)

Run the unchanged `PalletTown_EventScript_TryReadySignLady` from [Pallet Town's FireRed scripts](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/data/maps/PalletTown/scripts.inc#L15) in a browser and show the resulting FireRed scene variable. This exercises actual FireRed gameplay rules without waiting for the full title sequence, renderer, persistence or sound.

1. Generate a tiny script object from that label and the upstream `EventScript_Return` label. Expand the original `goto_if_unset`, `goto_if_ge`, `setvar` and `return` macros with FireRed constants. Use linker relocations for both branches to the return label; do not hand-author equivalent bytecode or assume ROM addresses. Generate a small dispatch table from the original slot numbers for `return`, `goto_if`, `setvar`, `compare_var_to_value` and `checkflag`; unused slots trap if reached.
2. Compile FireRed's `src/script.c`, `src/scrcmd.c` and `src/event_data.c` through the normal C preprocessing path for wasm32. Use function/data sections and linker GC for unrelated code, plus a tiny test harness that sets the relevant fields of a real `SaveBlock1`, selects stopped Quest Log playback, and uses the original script context and dispatcher. Guard the reachable file's ARM HALT instruction with a Wasm trap. If retained code requires Quest Log or full-game symbols, use explicit test-only traps for out-of-scope dependencies; a reached trap fails the probe. Preserve opcode indexes and use a correct typed table and bounds. Do not substitute a new dispatcher, flag store or command implementations.
3. Serve a small HTML harness that instantiates the module and invokes an export with three pairs of inputs. Only the inputs and output presentation live in JS; result computation stays in Wasm. Use the same module in an automated headless test.

| `FLAG_OPENED_START_MENU` | Initial `VAR_MAP_SCENE_PALLET_TOWN_SIGN_LADY` | Expected after running the script |
| --- | ---: | ---: |
| Unset | 0 | 0 (first branch exits) |
| Set | 2 | 2 (second branch exits) |
| Set | 0 | 1 (the original setvar runs) |

Accept the probe only if the Wasm link map/symbols show the upstream interpreter and handlers, all cases terminate in the browser with no unexpected import or trap, and opcode bytes/branch targets match the ARM assembly of the same script after normalizing addresses. Keep fixtures and generator versioned; keep binaries local. Changing only the input must change behavior through Wasm. This is a proof of the game-code and data path, not a claim that FireRed boots.

For replay, compare selected state and meaningful pixels against pinned FireRed, rather than treating the Emerald reference or a screenshot alone as an oracle.

## Data handling and primary risks

- **Rights and provenance.** Neither FireRed nor Emerald has a root license identified at these revisions; some individual host tools have their own license files. Treat both as references until redistribution rights are reviewed. Cricket's MIT license covers its repository code, not assets from the game. Keep private upstream checkouts, source inputs, generated assets, ROMs, saves and captures out of the port repository. Both Pokémon reference trees even contain tracked `data/mb_*.gba` multiboot blobs; do not vendor them. Do not publish Wasm or asset packs containing copyrighted game data or derived code without authorization. The audit needs no retail ROM, ROM upload, asset dump or public deployment.
- **Data conversion is the first critical risk.** Wasm32 matches the width of many GBA fields but not ARM function addresses, bitfield packing rules, address regions or all alignment assumptions. Add compile-time layout assertions and relocation probes before enabling whole-map or battle assets. Preserve raw operand widths and distinguish table indexes from addresses.
- **Timing and side effects are the next risk.** A renderer can look correct with wrong VBlank/HBlank, DMA or music status behavior. Check trace order, delays, RNG and waits as well as pixels. For save compatibility, depend on FireRed serialization and raw sector tests rather than a browser-only format masquerading as a cartridge save.
- **Scope control.** Milestones depend on the previous evidence. Avoid importing Emerald content, permitting silent default imports, or smoothing over an unsupported feature with a gameplay change. A clean compile or one passing route does not establish whole-game parity.
